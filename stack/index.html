HOW WE BUILD

Give AI coding assistants the right source.

GitHits connects our AI coding assistants to searchable public code and documentation. We use it to look up the exact version of an open-source dependency that a project uses.

WHY

AI answers can mix up software versions.

An AI coding assistant can mix up software versions: a renamed function, an option available only in unreleased code, or a security advisory published after training. Its answer may look convincing while failing against the version a project actually uses.

Reading the source at the project’s exact version gives the assistant evidence to check. GitHits indexes public open-source code, documentation, package metadata, vulnerabilities and changelogs by version, and makes them available through AI tool connections (MCP), a command-line tool and a web interface for software (REST API). The assistant can read the release recorded in the lockfile, which lists the dependency versions installed by the project.

WHAT WE WIRE UP

How we use GitHits.

01 / AGENTS

Code search inside our coding assistants

GitHits uses MCP, a standard connection between AI assistants and tools. Its server is configured in SyberLabs repositories, so coding agents such as Claude Code can search and read dependency source, docs and changelogs at a named version, and check vulnerabilities before updating a dependency.

02 / THIS SITE

Dependency panels at build time

Each project page carries a dependency panel generated from GitHits’ package API (api.githits.dev/v1) when the site is built: license, latest version and known vulnerabilities for the packages listed in the project’s dependency files. Only fields GitHits returned are shown. Where no saved report has been fetched yet, the panel says so.

SETUP

The exact commands.

On a developer machine, one command detects the installed coding agents, configures GitHits for them and signs in. Sign-in uses OAuth, which opens the provider’s sign-in page in your browser. The access token is kept in the system keychain.

npx githits@latest init

A repository can also register the hosted server for every agent that opens it, in .mcp.json; the first use asks for sign-in.

{ "mcpServers": { "githits": { "type": "http", "url": "https://mcp.githits.com" } } }

Automated builds (CI) and other runs without an interactive user have no browser for sign-in. An API token is stored as the repository secret GITHITS_API_TOKEN and exposed to the job as an environment variable. It is never committed or written to a file, and the build still succeeds without it.

# CI: token from the GitHits settings page, stored as a secret
env:
  GITHITS_API_TOKEN: ${{ secrets.GITHITS_API_TOKEN }}

# confirm the token is picked up
npx githits@latest auth status

Commands from the GitHits documentation as of 8 October 2026.

WHAT LEAVES OUR MACHINES

What we send to GitHits.

  • Build-time panels. The requests carry public package names and versions read from each project’s manifests. Nothing else from our repositories is sent.
  • Agents over MCP. A request carries the agent’s query and any context the agent puts in it. GitHits states that signing in gives it no access to private repositories and that it does not access, index, search or store private repository code; the agent keeps working on the local checkout. Because the agent writes the query, our repositories instruct it to name public packages, versions and APIs and never to send unpublished code, content, tokens, secrets or personal data. GitHits’ own docs give the same rule.
  • Retention. Per GitHits’ privacy policy, queries and outputs are kept for 90 days and MCP and API request logs for 30 days, and training on inputs is off unless a user opts in. Their policy governs; this is a summary as of 8 October 2026.
