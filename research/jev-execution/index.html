GROKCELL EXECUTION

What must run after

Choosing an action is only half the work. GrokCell Execution defines the application layer that enforces live permissions, reserves budgets, verifies candidate outputs, and recovers cleanly from crashes.

00 / ABSTRACT

What an application must own after a model’s answer.

Typed decision interfaces such as TypeSafe’s Jev (Choice, Noul, and Score) structure model outputs [1], but a valid choice does not guarantee current authorization, available budget, artifact correctness, or crash-safe durability.

GrokCell Execution wraps that boundary in a six-operation contract: read state, decide from permitted offers, call under reserved budget, check output deterministically, admit atomically, or yield without resetting limits. Our single-machine Python/SQLite prototype passes 87 regression tests and process-kill replay experiments across two offline fixtures [4]. Results verify specific crash-recovery properties, not live-provider quality or adversarial security isolation.

THE ABSTRACTION

A bounded execution attempt ending either in an evidence-bound revision or a logged stop reason.

01 / FIRST-PRINCIPLES DERIVATION

Four invariants models cannot own.

Every action consumes resources, runs under mutable permissions, can produce invalid outputs, and can crash mid-flight. None of those risks belongs inside the model:

  1. Application-owned authority. The application defines actions, expiry, and revocation; the model only picks among supplied offers.
  2. Upfront budget reservation. Reserve budget before dispatch and hold reservations across lost responses until reconciled.
  3. Input-bound evidence. Bind verification evidence to the exact candidate, dependencies, and checker contract; stale state invalidates acceptance.
  4. Atomic admission. Commit accepted revisions alongside evidence and journal state as one atomic transition.

Scope discipline: one coordinator, six operations, one authoritative local store. Distributed scheduling, services, workflow languages, and live providers wait until an accepted workload justifies them.

02 / EXECUTION CONTRACT

Six operations.

Operation boundaries
OperationOutputRequired boundary
readObservationBinds inputs to exact dependency and state revisions.
decideDecisionSelects one offered, permitted action.
callCandidateReserves budget before invoking worker.
checkEvidenceBinds mandatory checks to exact candidate.
admitAccepted revisionVerifies live authority, freshness, limits, and passing evidence.
yield_Paused runPersists pause without renewing deadlines or budgets.

Design specification, not a formal proof. With candidate c, evidence e, current state s, and permission p, admission requires:

admit(c, e, s, p) only if
  permitted(p, now) ∧ fresh(c, s)
  ∧ bound(e, c, dependencies, checker)
  ∧ all_required_checks_pass(e)
  ∧ within_limits(run)

commit(accepted_revision, candidate, evidence, journal)

The prototype verifier runs in-process as trusted application code. Its separate interface isolates responsibilities cleanly, but does not yet provide process isolation against a compromised machine.

03 / DURABILITY & FAILURE SEMANTICS

Three write barriers.

Optional state persists in a single SQLite database (rollback journaling, full sync, bounded versioned JSON, zero pickle or dynamic imports) guarded by an OS coordinator lock [2]. Filesystem and hardware durability assumptions still apply [3].

01 / BEFORE CALLBACK

Persist dispatch intent, step identity, and budget reservation.

02 / AFTER RESPONSE

Persist raw result and usage accounting before consumption.

03 / AT ADMISSION

Atomically commit revision, bound evidence, and terminal journal entry.

Restarts replay completed steps from the journal without re-invoking callbacks and halt on interrupted in-flight steps rather than resending blindly. This enforces conservative replay control, not remote exactly-once delivery. The prototype runs no live effects and includes no external reconciliation procedure.

Restarts verify configuration identity (permissions, budgets, dependencies, adapters, and checker contract), preserve original deadlines and revocations, and fail closed on missing, corrupt, or unsaved state.

Checksums catch accidental corruption, not adversaries who can alter the database. State is unencrypted (POSIX mode 0700; inherited permissions on Windows) and assumes a trusted local environment.

05 / LIMITATIONS & FOUNDATIONS

Limitations.

GrokCell Execution composes established systems primitives: typed decisions [1], application-owned authority, journaled intent, bound evidence, and atomic SQLite commits [2, 3]. We make no novelty claim over these foundations.

  • No live Jev or Hugging Face calls in this runtime. Chooser and worker run offline fixtures only.
  • No hostile-code sandbox. Imported Python adapters run with full application privileges and cannot be preempted if hung.
  • No remote exactly-once guarantee. Halted unknown steps prevent blind resends but require external reconciliation.
  • No certified backup, migration, or power-loss verification. Process-kill tests cover a narrower failure model.
  • No live task-quality, latency, or economic benchmark yet.

Explicit boundaries should improve inspectability and contain failure propagation; comparative evaluation is still required to prove operational value over simpler baselines.
