SyberLabs / The factory

How SyberWork handles a code change.

AI agents write and repair the code. SyberWork runs every check itself, logs each step in a signed record, and changes your branch only after a person approves.

The six steps

SyberWork calls one change to one repository a Build Thread. Each step below is logged, and each lists what it never does.

  1. 01

    Start

    Records the starting commit, the paths the change may touch and the version of the contract, the file that sets the checks, rules and budget.

    Never moves a branch or changes your working files.

  2. 02

    Context

    Picks the code excerpts the agent will read by matching file paths and symbol names, and logs why each was picked. It uses no embeddings.

    Never stores the excerpt text. It is read from Git again when the agent runs.

  3. 03

    Propose

    Models write proposed changes as Git commits on separate refs. By default SyberWork sends its own check results back to the model until a change passes or the budget runs out. The alternative is an evolutionary search. On SyberWork’s own benchmark fixtures the repair loop solved more tasks per dollar, so it is the default.

    Never edits your working files. A model’s report that its tests pass is logged as unverified and changes nothing.

  4. 04

    Check

    SyberWork runs the contract’s checks on the exact files in the proposed commit, in a new worktree with a scrubbed environment. It logs each check’s state, exit code and a hash of its output. A separate reviewer then examines the change. The reviewer is never the agent that wrote it, and a high-severity finding blocks approval.

    Never treats a model provider’s claim as a check result.

  5. 05

    Approve

    Twenty-one rules are evaluated in order, and the first one that applies decides. Agents and people are held to the same rules. A person accepts the change, or a second person with the required role approves it first.

    The only write moves the thread’s own branch, and only if that branch still points at the expected commit. No push, no merge, no change to main.

  6. 06

    Publish

    Pushing the branch, opening a pull request and publishing a package are separate actions. Each goes through the rules, is logged, and can be retried or reconciled safely.

    Accepting a change never publishes it.

What the record contains

Check results SyberWork produced itself
Every check result comes from a process SyberWork started on files it wrote. None comes from an agent’s report.
A signed hash chain
Every event is added to a hash chain. A separate process holds the signing key, signs the latest hash in the chain and appends it to an append-only log.
Spend against a budget
The contract can set a price for each model. SyberWork measures the spend, stops a search at its dollar limit, and rejects a change that cost more than the thread’s budget.
Metrics for each work item
Each work item reports its cost, turns, agent time, fix rounds, lookups, review rejections and human interventions. Each number traces to the events it was computed from.

SyberWork is built with SyberWork

SyberWork’s own pull requests go through a Build Thread before they merge. The repository checks out the change, proposes it, runs its tests and conformance checks on those exact files, and approves it under the same rules. Each pull request shows who approved it, the rules review and the check results.

The GitHits client and its Claude Code integration were built this way.

Limits

  • Checks run in a temporary worktree with a scrubbed environment. That is not a sandbox, so untrusted agent code runs as a separate command.
  • An approved change is tested: the named checks passed on those files. That does not show the change is correct, wanted, measured or deployed.
  • The hash chain is evidence of integrity only as far as you trust the database that stores it. It is not a public transparency service.
  • Browser checks of documentation run in Attest, a local command-line tool. There is no hosted service yet.
